# 宝宝今天穿什么：首次使用与增长体验诊断

日期：2026-09-20｜项目：F:\miniwear｜状态：**已完成开发者工具中的核心路径体验与方案设计**。本轮没有修改产品代码。

## Product Diagnosis

**最值得先做的，是让用户尽快得到可信的穿搭，并让已经做出的选择真正生效、能够保留。** 目前最明显的障碍发生在首次获得结果，以及用户尝试修改、确认结果的时候。增加功能或整体换视觉风格都不是第一优先级。

产品面向宝宝父母及共同照护者，帮助把室温、天气和宝宝情况转换为“在家 / 出门 / 睡觉”的穿衣参考。目标用户年龄范围来自现有规则，实际用户构成尚无数据验证。

| 定义 | 本产品中的含义 |
| --- | --- |
| Core Problem | 知道温度，仍不确定该给宝宝穿什么，也不容易向家人交接 |
| Core Value | 得到具体搭配，理解适用条件，并按当前情况调整 |
| Core Action | 看懂一个当前适用的场景结果，能够选定一套搭配 |
| Aha Moment | “原来这个温度可以这样穿，我知道下一步怎么做了”——仍需真实用户验证 |
| Activation | 首次完成上述判断；填完资料、生成示例或点击分享不能代替激活 |
| Retention Driver | 出门前、睡前和环境变化时重新判断；复用已确认的信息，减少第二次任务成本 |
| Sharing Motivation | 将具体照护决定交给共同照护者，而非泛化邀请别人使用工具 |

**值得保留的体验：** 不要求账号、手机号；城市可搜索手选；三场景符合照护任务；建议、调整按钮和提示在本次设备上能完整呈现于首屏；冷热帮助可展开；图鉴有实际图片；海报能生成；隐私说明明确表达本地保存。奶油底色、珊瑚橙和场景图标有一致性，建议延续。

另有先前的 [11 组独立状态回放](evidence.json) 及 [复现脚本](replay.cjs)，用于补充手动数据时间、断网与旧缓存分支。这些是隔离逻辑回放，**不冒充原生 UI 或真实网络失败测试**。本轮新增的结构化实测摘要见 [live-evidence.json](live-evidence.json)。

未验证：物理真机手感、小屏/大字模式、真实定位拒绝及相册授权、真实好友接收和扫码、跨日真实使用、医学建议的有效性、线上转化与留存。没有向外发送分享内容，也没有保存海报到用户相册。体验产生的测试资料和天气已移除，原有本地数据逐项恢复并核验一致。

本次全跳过再生成的最短路径是 **5 次按钮动作**：跳过 × 3 → 手动填写 → 生成。不含读页面、改温度和确认条件的成本。由于自动化通信与分析会干扰计时，不把本轮操作时长当作 Time to Value。

## Top Problems

仅保留 7 项，按用户任务影响与证据确定性排序。没有真实流失数据，以下流失原因是待验证的解释。

1. **“改天气”没有改变结果依据。** 用户输入 30℃，产品仍用 25℃，直接损害控制感和信任。
2. **“刚刚好”撤销调整，返回也丢失选择。** 按钮语义与用户预期冲突。
3. **首次价值被三步设置和天气条件挡住。** 室温已确认也不能独立完成在家任务。
4. **默认、实测、手填和旧数据不够清楚。** 用户未必知道结果依据来自哪里、是否仍然适用。
5. **结果能看到，但理解衣物与采纳的动作不够突出。** 最大的珊瑚色按钮是分享，图鉴与当前建议分离。
6. **分享预览可用，接收价值尚未闭环。** 海报保存需要后续操作；普通转发入口没有携带当前结果上下文。
7. **回访没有明确延续上次判断。** 已有资料复用，但缺少“上次决定 + 本次条件变化”的承接。

## Priority Changes

### 1. 让手动修正成为真正生效的选择

- **Problem / Evidence：** 有城市实时天气时，从“改天气”输入 30℃并生成，出门建议仍明确依据 25℃。这是已实测的操作失败。
- **Why users may leave：** 用户会反复修改、误以为自己操作错误，或放弃相信建议。
- **Change：** 明确两种来源：“自动天气 / 手动填写”。提交手动值即切换为手动来源，结果立即按该值重新计算，并显示“手动 30℃ · 刚刚填写”。用户主动点“恢复实时天气”才切回；普通页面返回或自动刷新不得静默覆盖。新场景或条件过期时询问是否更新，避免无限沿用。
- **Expected behavior：** 从重复提交或放弃，变成一次修正后继续选择搭配。
- **Metric：** 有效手动提交后，展示依据与提交值一致率；短时间重复改温比例；任务完成率。
- **Impact / Confidence / Effort：** 高 / 问题高、增长收益待验证 / 低至中。
- **Hypothesis：** 用户可预测并控制输入来源，才会愿意依赖和再次使用结果。

### 2. 让确认保留当前搭配，浏览返回也不撤销

- **Problem / Evidence：** “刚刚好”重置调薄结果；从图鉴返回也清除调整，两条路径均实测复现。
- **Why users may leave：** 刚做完的选择消失，无法确定家人看到的是否还是自己认可的那套。
- **Change：** 先修正确认和返回时的保留行为。进一步把“刚刚好”改为“记下这套搭配”，保留当前场景、条件及最终选择；将“恢复默认建议”独立为低权重操作。“穿后偏热 / 合适 / 偏冷”作为穿着后的反馈，避免与采纳混用。条件改变时解释需要重新判断，不静默重置。
- **Expected behavior：** 从反复试按钮，转为完成一次选择；看图鉴或设置后继续原任务。
- **Metric：** 确认后结果保持一致率、浏览返回保留率、确认后的重复调整/确认比例、采纳率。
- **Impact / Confidence / Effort：** 高 / 操作冲突高、收益待验证 / 保留修正低，记录设计中。
- **Hypothesis：** 明确区分调整、采纳、穿后反馈与重置，能减少误操作。一次“合适”不应永久修改宝宝体质判断。

### 3. 先完成一个场景，再完善资料

- **Problem / Evidence：** 三次跳过后没有结果；只确认室温也无法看在家建议。第一屏主内容讲“天气基准”，尚未展示具体能帮用户做什么。
- **Why users may leave：** 还没看到价值就进入设置，跳过后仍被要求补条件。
- **Change：** 首屏一句话说明用途：“按当前温度，看看宝宝在家、出门和睡觉怎么穿”，配一份明确标为示例的搭配。一个主入口“看看现在怎么穿”。随后按场景确认必要条件：在家/睡觉使用室温，出门才需要室外条件；月龄用简短年龄段确认，详细生日和非必要资料后置。必要信息未知时展示标识清楚的示例，不伪装成个人建议。
- **Expected behavior：** 从连续跳过或退出，转为完成一个眼前场景的真实判断。
- **Metric：** 首次有效结果率、首次会话激活率、TTFV 中位数/P75；按场景及无天气状态分组。
- **Impact / Confidence / Effort：** 高 / 路径阻断高、转化收益待验证 / 中至高。
- **Hypothesis：** 场景所需条件比完整资料更适合成为第一次任务入口；应在设计原型中先验证。

### 4. 把“依据是什么、什么时候的”说清楚

- **Problem / Evidence：** 手动页预填室外 21℃，资料未填时默认按 6 个月；手动模式来源文案在截图中被截断。旧缓存和手填时间问题由隔离回放补充，未做真实跨日验证。
- **Why users may leave：** 发现某个默认值与现实不符后，容易怀疑整份建议。
- **Change：** 结果上方用短行显示当前场景、温度、来源、更新时间和必要的资料状态。区分“已确认 / 示例 / 上次填写”；手填记录时间，旧数据显示“昨天 16:00”，需要重新确认时给原位入口。状态说明用足够可读的字号和对比，不把依据埋在设置里。
- **Expected behavior：** 用户能发现并纠正关键条件，知道这份建议为什么适用于当前任务。
- **Metric：** 来源理解正确率、关键条件确认率、过时依据沿用率；同时观察是否增加首次任务时间。
- **Impact / Confidence / Effort：** 高 / 界面与数据事实高、用户误解待验证 / 中。
- **Hypothesis：** 透明依据能够增加信任；不能把更多确认点击当成增长。

### 5. 保留现有视觉结构，把重点从分享移到选定搭配

- **Problem / Evidence：** 本次首屏能容纳完整建议，没有证据支持为“结果看不到”而重做首页。但视觉上最强的是“分享给家人”，确认按钮较弱；当前建议不能就地查看衣物图例。图鉴横向列表首屏恰好显示 3 张完整卡，后续内容的可发现性需要验证。
- **Why users may leave：** 看到了名称却不认识衣物；去图鉴查找打断当前任务，或者还未选定就被引向分享。
- **Change：** 保留奶油底、场景切换和结果卡。让具体搭配与“记下这套搭配”成为主要层级；分享降为次要动作。衣物名称可打开对应图例与替代项，复用已有素材；图鉴卡能进入解释，横向列表露出下一张卡的一部分。辅助文字提高可读性，长来源文案改短标签。不要为美化增加多层卡片或塞满产品图。
- **Expected behavior：** 读懂结果、认出衣物、完成选择；需要帮助时在当前任务内解决。
- **Metric：** 五秒用途理解、衣物辨认正确率、图例返回后的任务完成率、采纳率。图鉴停留时间和点击数只作诊断。
- **Impact / Confidence / Effort：** 中高 / 视觉事实高、行为收益待验证 / 中。
- **Hypothesis：** 就地解释和清晰主次比整体换风格更能帮助用户行动。图鉴“保暖值 +X℃”的理解与依据需另行验证，不把它引导为用户自行相加的穿衣公式。

### 6. 分享当前决定，让家人打开就能看懂

- **Problem / Evidence：** 实测海报可生成且已有小程序码，不能将其描述为缺失。主要动作是保存图片；海报没有明确生成日期。补充检查发现普通转发指向今日页，未携带当前结果；好友端实际体验未验证。
- **Why users may leave：** 发送者需要继续操作相册/聊天；接收者希望立即看结果，普通入口可能让其重新设置。
- **Change：** 在采纳后提供“把这套建议发给家人”，设计原生转发当前结果的路径，保留保存图片。分享内容包含日期、场景、已确认条件、最终搭配及必要提示。接收页先显示只读参考，再提供“按我家情况生成”；失效内容说明原因并提供更新出口。仅传必要信息，不传生日或精确位置。
- **Expected behavior：** 发送者交接已经选定的搭配；接收者先获得信息价值，再自主决定是否生成自己的建议。
- **Metric：** 分享意图、可归因接收访问、结果有效查看、接收后自有结果生成；协作成功与获客分别统计。
- **Impact / Confidence / Effort：** 中高 / 发送端高、接收端与增长潜力待验证 / 中至高。
- **Hypothesis：** 共同照护是自然的分享理由。保存图片或打开分享面板不等于实际发送；接收者只读成功也有价值。

### 7. 让第二次使用接着上一次判断继续

- **Problem / Evidence：** 已有本地资料复用，但没有上次采纳内容和条件变化的清晰承接；浏览返回调整丢失已实测，跨日需求仍是产品假设。
- **Why users may leave：** 每次重新判断都像从头来过，用户感受不到重复使用能减少什么工作。
- **Change：** 回到上次场景，显示“上次确认”与“当前条件是否变化”，提供“按现在情况更新”。只在有可靠可比记录时描述温差，不编造“比昨天更凉”。历史搭配明确标时间；条件过时先确认，不直接沿用为今日建议。先做简洁的本地记录，不先增加签到、积分或订阅提醒。
- **Expected behavior：** 出门前、睡前或环境变化时主动回来，以更少操作完成第二次判断。
- **Metric：** 第二次有效使用率、第二次 TTFV、首次激活用户的 D1/D7 有效留存。
- **Impact / Confidence / Effort：** 中高 / 当前能力缺口高、留存动因待验证 / 中。
- **Hypothesis：** 延续有用的决定比制造打开理由更适合该产品；上线前需确认用户是否实际需要记录。

## UI / UX Changes

以下是本轮交付的**设计方案，不是已实现界面**。重大流程调整以此为讨论和原型验证依据；本轮未进入代码修改。

### A. 首次体验：用途 → 必要条件 → 单场景结果

当前：首次打开 → 城市 → 室温 → 资料 → 今日页 → 条件不足时再去手填。

方案：
1. 首屏说明用途，展示标明“示例”的搭配，主入口“看看现在怎么穿”。
2. 选择在家/出门/睡觉，同页填写该场景必要温度和年龄段；已有确认信息可复用。
3. 主按钮随场景写成“查看在家穿搭”等，直接进入结果。
4. 出门天气失败时在原位手填；在家/睡觉仍独立可用。详细资料后续完善。

原因：先解决具体任务，同时让必要条件透明。验证首次结果率、用途理解和 TTFV，不能把示例曝光计为激活。

### B. 今日结果页：保留骨架，明确依据、主动作和来源

建议的信息顺序：

> 在家 / 出门 / 睡觉<br>
> 室外 30℃ · 手动填写 · 刚刚　[修改]<br>
> **具体搭配**　[看衣物图例]<br>
> 一句推荐原因<br>
> [薄一点]　[厚一点]<br>
> **[记下这套搭配]**<br>
> [恢复默认建议]　[发给家人]<br>
> 冷热应对与必要使用提示

这是交互层级示意，不要求新增页面或大幅移动现有模块。温度来源编辑中并列“自动 / 手动”；切换来源后给清晰反馈。用户确认后显示持久的“已记下”，浏览图例返回仍是当前结果。穿后反馈在之后出现，不抢占首次采纳。

原因：用户先理解、调整和决定，分享随后发生。验证输入生效率、返回一致性、任务完成率和误操作。

### C. 回访：保留场景，先判断条件是否变化

当前：回今日页重新加载并清除调整。

方案：回到上次场景 → 看到上次记录时间与条件 → 必要时确认当前温度 → 更新结果。仍使用今日页，历史简洁展开。条件未改变且仍有效时减少重复填写；条件变了时解释为什么重新推荐。

原因：降低第二次任务成本。验证第二次有效使用和第二次 TTFV；是否提升留存需真实数据。

### D. 分享接收：先读交接，再决定是否自己生成

当前：海报预览 → 保存图片 → 用户自行发送；普通转发进入工具首页。

方案：采纳当前搭配 → 分享该场景快照 → 接收页显示日期、条件与搭配 → 家人读懂交接，或点击“按我家情况生成”。接收页不因未建档而挡住只读内容。过期或内容不可读时保留明确出口；海报也添加日期。

原因：分享承诺与落地体验一致。验证发送和接收两端任务，不能仅用分享按钮点击证明闭环。

加载、错误、空状态原则贯穿以上设计：只阻断缺少必要条件的场景；旧内容明确标旧；手动提交失败保留输入；生成/保存图片失败保留可重试出口；无需再次填写已确认且仍有效的信息。

## Growth Opportunities

建议按依赖关系推进，而非一次重做所有页面：

- **第一批：1 + 2。** 修正手动输入和确认/返回的语义，使已有能力可信。这两项实测证据最强，也不需要整体重设计。
- **第二批：3 + 4 + 5。** 先验证首次流程原型，再实现按场景取值、依据透明和结果就地解释。目标是第一次真正完成任务。
- **第三批：6 + 7。** 在核心任务可靠后，验证家庭交接与第二次使用。不要在未完成采纳前用强分享按钮代替增长设计。

Activation 来自第一次完成判断；Retention 来自下一次判断更省事；分享增长来自具体内容对家人的价值。没有证据支持现在优先做账号、打卡、积分或更多栏目。

## Metrics

本轮没有线上漏斗、真实留存或用户访谈数据，也没有新增线上埋点。以下是验证方案，**不是已取得的增长结果**。

| 项目 | 最小事件/任务观察 | 核心口径 |
| --- | --- | --- |
| 1 输入生效 | manual_context_submitted、recommendation_visible | 有效提交后，依据温度/来源与提交一致的比例；重复改温率 |
| 2 选择保留 | recommendation_adjusted、outfit_saved、scene_returned | 确认及返回后的结果一致性；有效结果用户中的采纳率 |
| 3 首次价值 | first_open、context_confirmed、recommendation_visible | 首次会话有效结果人数 / 首次打开人数；TTFV 中位数与 P75 |
| 4 依据理解 | context_source_shown、context_corrected；访谈复述 | 能正确说出来源、时间和适用条件的比例 |
| 5 搭配理解 | garment_help_open、garment_help_return；辨认任务 | 正确认出衣物并完成选择的比例 |
| 6 分享价值 | share_intent、poster_exported、shared_result_visible、own_result_visible | 接收有效查看、自有结果生成；协作与获客分开 |
| 7 回访 | session_start、context_refreshed、recommendation_visible | 第二次有效使用、第二次 TTFV；首次激活后第 1/7 个自然日有效留存 |

口径约束：
- 有效结果必须在屏幕可见，且必要条件已经确认；示例不计入激活。事件只能代理“获得价值”，需结合用户是否看懂、能否选定来验证。
- TTFV 从首屏可交互到首个有效结果可见，同时报告未完成比例，不能只看成功者耗时。本轮没有可用的秒数基线。
- “记下”代表采纳意图，不证明实际穿着或舒适。分享面板/导出图片也不证明发送成功；纯图片的接收归因不足应单列。
- 埋点只需任务状态、场景、来源类型和时长，不需要上传生日或精确位置；采用何种统计方案另行确定。

先做 5–8 位未使用过产品的照护者任务测试：五秒复述用途、无定位完成在家任务、把室外改到指定温度、调薄并确认、查图例返回、再次使用及接收家人分享。记录是否完成、误解、犹豫和实际用时。这是探索性样本，不能用于声称总体增长幅度或统计显著性。
